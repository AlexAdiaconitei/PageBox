# Revisión de seguridad y funcionamiento, 5 de octubre de 2026

Se revisaron las sesiones del panel y del lector, aislamiento por host, permisos, tokens, subidas ZIP, cuotas, locks, retención, borrados y respuestas HTTP. Las correcciones están en este checkout. No se ha publicado ni desplegado la aplicación.

## Problemas corregidos

| Problema | Comportamiento anterior | Corrección |
| --- | --- | --- |
| Cambio obligatorio de contraseña | Repetir la contraseña temporal como contraseña nueva eliminaba el bloqueo y abría el panel. | Se exige una contraseña distinta y se conserva el bloqueo cuando se rechaza el cambio. |
| Cookies en HTTP | La copia de Set-Cookie omitía Secure=false y SvelteKit añadía Secure por defecto. Un navegador en un dominio HTTP podía perder la sesión. | La copia preserva explícitamente Secure y HttpOnly. Las cookies HTTPS siguen usando Secure y el prefijo __Host-. |
| Roles de grants | El formulario aceptaba un rol arbitrario y lo escribía como texto en la base de datos. | Solo se admiten viewer, deployer y owner. |
| Caducidad de tokens | Valores negativos o NaN generaban tokens sin caducidad; valores fuera del rango de Better Auth podían provocar un 500. | Se aceptan únicamente 0, sin caducidad, o días enteros entre 1 y 365. Los valores inválidos devuelven 400. |
| Rangos fuera del archivo | El error 416 de S3 se propagaba como 500. | Se validan y normalizan rangos antes de consultar S3. Un rango imposible devuelve 416 con Content-Range y sin caché. Los rangos malformados o múltiples se ignoran. |
| If-Range | Se devolvían bytes parciales aunque el cliente tuviera otra versión del archivo. | Un ETag o fecha que no coincide produce la respuesta completa. Se rechazan validadores débiles. |
| 404 propio del sitio | If-None-Match podía convertir un 404 en 304 y Range podía convertirlo en 206. | Las respuestas 404 mantienen el estado y el documento completo. |
| Compresión | Se elegía Brotli por coincidencia parcial del nombre, se ignoraban pesos y no se intentaba gzip si faltaba Brotli. | Se comparan nombres completos, se respetan pesos y rechazos, y se prueban los formatos aceptados por orden. |
| Errores y redirects privados | Faltaba Cloudflare-CDN-Cache-Control en las respuestas 401 y 302 del guard de permisos. | También llevan la prohibición explícita de caché de Cloudflare. |
| Configuración y documentación | CSRF usaba una opción obsoleta, CSS contenía un pseudo-elemento inválido y README describía una revisión pendiente y un permiso de borrado incorrecto. | Se usa la configuración vigente con el control de origen en hooks, se elimina el selector inválido y se corrige README. |

Los defectos de contraseña, cookies, roles, compresión, rangos, If-Range y 404 se reprodujeron con pruebas que fallaban contra el build anterior. Las regresiones HTTP utilizan la aplicación compilada y PostgreSQL/MinIO desechables. La nueva prueba de atributos de cookies comprueba tanto la ausencia de Secure en HTTP como la conservación de HttpOnly.

## Pendientes externos

Queda pendiente actualizar cuando exista un parche.

La publicación de 0.2.0 y la comprobación de DNS wildcard, proxy y TLS del despliegue siguen pendientes. La revisión local no accedió al homelab. El procedimiento está en [DEPLOYMENT-SECURITY.md](../DEPLOYMENT-SECURITY.md).

Las reglas de rangos, If-Range y precondiciones se contrastaron con [RFC 9110](https://httpwg.org/specs/rfc9110.html#field.if-range). La sustitución de checkOrigin por trustedOrigins sigue la [documentación de SvelteKit](https://svelte.dev/docs/kit/@sveltejs-kit-vite#csrf); el hook de PageBox comprueba el origen completo antes de resolver las rutas.
