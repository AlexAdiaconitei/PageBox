PageBox ships as an image, so the shortest route is an application that pulls it — no build
step on your server, and the version you run is a version somebody tagged.

```
ghcr.io/alexadiaconitei/pagebox:0.1.0
```

| Route | Use it when |
| ----- | ----------- |
| **Application → Docker** | almost always: pull a released tag, *Add Domain* works |
| Application → Dockerfile | you are running a fork, or a commit that has no tag |
| Compose | you already manage the stack as compose — routing is then yours to write |

## Two domains, one container, one port

This is the part that surprises people, so before the steps: **PageBox is one process
listening on one port.** Not two containers, not two ports, and not two paths. Which of the
two surfaces a request reaches is decided by the `Host` header, before routing happens:

```
Host: pagebox.example.com   →  the panel and the API
Host: pages.example.com     →  the hosted sites, under /s/<slug>/
Host: anything else         →  404
```

In Dokploy that means **one application with two domains on it**, both pointing at
container port `3000`. Traefik matches the hostname and forwards to the same container;
PageBox reads the forwarded host and picks the surface.

<Callout type="warn" title="Why not two ports, or two paths">
Neither one separates what has to be separated. The sites host runs JavaScript somebody
else uploaded, and the panel's cookie has to be unreachable from it.

**Ports do not isolate cookies.** A cookie set on `example.com:3000` is sent to
`example.com:3001` too — the cookie jar is keyed by host, not by origin. A second port
would look like a boundary and enforce nothing.

**Paths are the same origin outright.** With `example.com/panel` and `example.com/sites`, a
page you host could `fetch('/panel/api/v1/…')` with your admin cookie attached and act as
you. It would also put every hosted site one directory deeper, which is the
[base path](/docs/deploy/base-paths) problem again, doubled.

Different hostnames are the only split browsers enforce for cookies, so that is the one
PageBox uses — and it refuses to start if the two are equal.
</Callout>

Both are single-level names under a domain you already own, so one wildcard DNS record and
one wildcard certificate cover them. There is no per-site DNS: a new site is a new path on
the sites host, never a new hostname.

## Application → Docker

<Steps>

<Step>
### Create the application
**Create Application**, then in *General* set the provider to **Docker** and the image to:

```
ghcr.io/alexadiaconitei/pagebox:0.1.0
```

The package is public, so no registry credentials are needed. Pin the exact version rather
than `latest`: `latest` moves under you on the next release, and a redeploy pulls again.
</Step>

<Step>
### Add both domains
*Domains* → **Add Domain**, twice, on this same application:

| Host | Container port | HTTPS |
| ---- | -------------- | ----- |
| `pagebox.<your-domain>` | 3000 | on, Let's Encrypt |
| `pages.<your-domain>` | 3000 | on, Let's Encrypt |

Same application, same port, two hostnames. If you find yourself creating a second
application, or typing a port other than 3000, stop and re-read the box above.
</Step>

<Step>
### Environment
*Environment* → paste and fill in. Nothing here has a safe default:

```bash
PAGEBOX_ADMIN_HOST=pagebox.<your-domain>
PAGEBOX_SITES_HOST=pages.<your-domain>
PAGEBOX_PUBLIC_SCHEME=https

DATABASE_URL=postgres://pagebox:…@<pg-host>:5432/pagebox
# REDIS_URL=redis://<valkey-host>:6379      # required past one replica

S3_ENDPOINT=http://<garage-or-minio>:3900   # anything that speaks S3
S3_ACCESS_KEY=…
S3_SECRET_KEY=…
S3_BUCKET=pagebox
S3_FORCE_PATH_STYLE=true

AUTH_SECRET=<openssl rand -base64 48>
BOOTSTRAP_ADMIN_EMAIL=you@example.com
BOOTSTRAP_ADMIN_PASSWORD=<replaced at first sign-in>

MAX_UPLOAD_BYTES=100MB                      # see below
PAGEBOX_STORAGE_BYTES=1GB                   # what this instance has to give away
PAGEBOX_DEFAULT_QUOTA_BYTES=1GB             # never above the line above
```

Sizes take a unit — `1GB`, `1gb`, `500MB`, `1.5GB`, `2TB` — or a plain number of bytes.
Units are 1024-based, and `GB` and `GiB` mean the same thing, so the panel prints back what
you typed.

`PAGEBOX_STORAGE_BYTES` is what the panel divides into quotas: allocated, free, and a
superadmin whose own room is whatever the admins leave over. It is a **declaration, not a
measurement** — S3 has no capacity API — so write down what the bucket's disk actually has.
Leave it out and per-admin quotas still hold; there is simply no pool.

<Callout type="warn" title="A small pool needs a smaller default quota">
`PAGEBOX_DEFAULT_QUOTA_BYTES` may not exceed `PAGEBOX_STORAGE_BYTES`, and it defaults to
**5 GB**. Declaring a 1 GB pool without lowering it refuses to start — deliberately, because
a default nobody could ever be given is better caught at boot than at the first attempt to
seat an admin.
</Callout>

The two hostnames must match the two domains you just added, exactly: they are what the app
compares the incoming host against. A domain Traefik routes but the app does not know
answers 404.

PageBox creates the bucket itself if the key is allowed to; otherwise create it first. The
proxy headers (`HOST_HEADER`, `PROTOCOL_HEADER`) and `BODY_SIZE_LIMIT` are set by the
image's entrypoint — leave them alone, and never set `ORIGIN`.
</Step>

<Step>
### Health check
*Advanced* → health check → path `/healthz`, port 3000.

It probes Postgres and S3 and answers on any host, including Dokploy's internal IP probe, so
a dependency outage marks the container unhealthy rather than letting it serve errors.
</Step>

<Step>
### Deploy
The first boot migrates, creates the bucket and creates the first account, then says so:

```
[pagebox] migrations applied
[pagebox] bucket "pagebox" created
[pagebox] bootstrap superadmin created: you@example.com (must change password at first login)
[pagebox] ready in 336ms · admin=pagebox.<domain> sites=pages.<domain>/s/<slug>/ cache=memory upload-cap=100 MB
```

Open `https://pagebox.<your-domain>/`, sign in, replace the password. Then
[put a site on it](/docs/start/first-site).
</Step>

</Steps>

## Application → Dockerfile

Same domains, same environment, same health check. The only difference is the source: point
the application at the Git repository and set Build Type to **Dockerfile** (`./Dockerfile`,
no build arguments). Your server then builds the image on every deploy, which takes minutes
instead of seconds and needs enough memory to run a Vite build.

Worth it for a fork. Not worth it to run a release.

## Compose, only if you must

`docker-compose.dokploy.yml` runs the app alone against services you supply, and pulls the
same published image. Two things to remember:

- Compose stacks in Dokploy **ignore** *Add Domain* and container labels for routing. Copy
  [`deploy/traefik-dynamic.example.yml`](https://github.com/AlexAdiaconitei/PageBox/blob/main/deploy/traefik-dynamic.example.yml)
  into Dokploy's dynamic configuration directory — usually
  `/etc/dokploy/traefik/dynamic/pagebox.yml` — and adjust the two hostnames and the
  container name. Both routers point at one service: the same split as above, written by
  hand.
- The service must be attached to `dokploy-network`.

## Upgrading

Deployments are immutable objects in S3 and the schema migrates forward on boot, so an
upgrade is a new tag and a redeploy: change the image tag, press Deploy, watch the log for
`migrations applied`. Take a database backup first when you skip a version. Nothing in the
object store is rewritten by a migration.

Rolling the *application* back is the previous tag. Rolling a *site* back is unrelated and
never needs a redeploy — it is a pointer move in the panel.

## Things that bite

<Accordions>

<Accordion title="Both hostnames must differ">
If they match, the container exits at boot with an explicit message. That is intentional: a
shared origin lets any hosted page call the admin API with your admin cookie.
</Accordion>

<Accordion title="A domain Traefik routes but the app does not know answers 404">
Traefik and PageBox each keep their own list. Adding a domain in Dokploy without adding it
to `PAGEBOX_ADMIN_HOST` or `PAGEBOX_SITES_HOST` gets you a certificate, a working route, and
a 404 on everything behind it — the unbranded one, because at that point PageBox has no idea
whose request it is.
</Accordion>

<Accordion title="Cloudflare and the upload cap">
`MAX_UPLOAD_BYTES` defaults to 100 MB because Cloudflare's proxy rejects larger request
bodies on non-Enterprise plans, and Cloudflare is the first deployment target. Raise it when
nothing in front imposes a smaller cap — it propagates to adapter-node's `BODY_SIZE_LIMIT`
automatically, so the app-level and HTTP-level caps cannot drift apart. Traefik itself does
not cap bodies unless you add a `buffering` middleware.
</Accordion>

<Accordion title="Cloudflare Access in front of the panel breaks CI">
The token-based API lives on the admin host. Either add a bypass policy for `/api/v1/*` or
send service tokens (`CF-Access-Client-Id` / `CF-Access-Client-Secret`) from the workflow.

Never put Cloudflare Access in front of the **sites** host — public sites would stop being
public.
</Accordion>

<Accordion title="Scaling past one replica requires REDIS_URL">
The app refuses to start otherwise, because the grant cache would be per-process and two
replicas would disagree about who can read what.
</Accordion>

<Accordion title="Do not set ORIGIN">
The app reads `x-forwarded-host` and `x-forwarded-proto`, which Traefik sets and the image's
entrypoint already points it at. A fixed `ORIGIN` collapses the two hostnames into one and
disables the host split — the property the whole design rests on.
</Accordion>

</Accordions>
